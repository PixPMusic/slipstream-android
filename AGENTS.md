# Working on Slipstream for Android

Read [CONTRIBUTING.md](CONTRIBUTING.md) before changing code or opening a PR.
Keep the solution small, native, and focused on one underlying problem.

## Repository map

- `app/` is the only module. `data/` holds models, API access, encrypted session
  storage, and demo fixtures; `ui/` holds sign-in, the library/drawer, theme,
  icons, and player.
- `app/src/test/` holds JVM unit tests with synthetic fixtures.
- `scripts/` holds the icon generator; `docs/` describes CI, Play releases, and
  privacy. `.github/workflows/` owns CI and the Play release.

## Implementation and verification

- Inspect the working tree and preserve unrelated changes. Use the intended
  base; ordinary PRs target `main`, while stacks name their parent explicitly.
- Consider phones, tablets, and foldables when changing shared UI. Check compact
  and expanded widths, insets, orientation, dark mode, Picture-in-Picture, and
  Android versions before 12 (no dynamic color) when relevant. State which
  surfaces were exercised and which remain unchecked.
- For logic, data, or state bugs, reproduce with a focused failing test before
  fixing when practical. Extend existing unit tests with synthetic fixtures.
- Purely visual fixes use matched before/after captures as proof; do not add
  tests that only mirror layout or copy. Interaction changes also need a short
  recording when still images cannot show the result.
- Exercise the affected app on an emulator or device. A successful build or
  desktop browser viewport does not establish Android behavior, and an emulator
  does not establish physical-device playback or foldable hinge behavior.
- Capture the original behavior before editing. Attach evidence to the PR using
  the [upload workflow](CONTRIBUTING.md#upload-pr-evidence). Local file paths and
  “screenshots retained locally” do not provide evidence to reviewers.
- Report unavailable access and verification gaps honestly. Do not claim an
  untested surface works or fabricate a before capture after applying the fix.

## Data, devices, and cleanup

- Prefer **Try Demo** and synthetic content for public evidence. Screenshots
  may show ordinary app UI, including the username and subscribed creators;
  those do not require sanitizing. Never expose cookies, credentials, other
  secrets, real hostnames, unrelated private content, or workplace/customer
  information.
- An authorized signed-in account may be used for playback verification. Preserve
  existing sign-in: do not sign out, clear app data, or uninstall the app unless
  explicitly requested. Prefer demo mode when synthetic content is sufficient.
- Keep evidence, scratch notes, build products, `local.properties`, keystores,
  and service-account files out of commits. Do not change the application ID or
  signing to make a PR build locally.
- Use at most one simulator or emulator at a time. Check for sessions used by
  other work; do not stop or take over someone else's device session.
- In T3 Code, use `device_list`, `device_open`, and its returned AgentDevice
  command to operate devices, then `device_screenshot` to inspect them.
- Stop only the processes, Gradle daemons, and device sessions you started,
  unless asked to leave them running. Do not kill by name or pattern.

## Publishing

Use the configured contributor identity. Keep AI authorship, coauthor, and
“generated by” footers out of commits. Disclose the actual full model name and
harness in the PR body as described in CONTRIBUTING.md. Preserve bot-managed
body blocks when editing a PR. Never merge a PR or dispatch a Play release
unless explicitly asked.
